What we will do

We start from an empty repository and build up: a branch, a couple of commits, a pull request, and one deliberate merge conflict that we fix together. By the end you will have pushed to a repository and reviewed somebody else's change, which is most of what working on a club project involves.
Before you come — setup
01Install Git — the setup guide in our library covers Windows and macOS
02Make a free GitHub account and bring the login
03Any editor you like — we will use VS Code on the projector
Could not get it working? Come at 5:45 and an officer will sit with you, or ask in #help.

One 45-minute standup a week after the general meeting, plus whatever you do on your own time — most contributors spend two to four hours a week. A pull request is how one person proposes a change and another person agrees to it. Everything below assumes you have Git installed and can clone a repository; if not, start with the terminal session in the archive.

1. Get the repository onto your machine

Club projects give contributors write access, so you clone directly rather than forking. Copy the URL from the green button on GitHub, then clone it and open the folder in your editor. If you are contributing to a project outside the club, fork it first — the difference matters only for where your branch lives.
git clone git@github.com:cssec-fgcu/eaglefind.git
cd eaglefind
git checkout -b your-name/item-search

2. Make one change, not five

A reviewable pull request does one thing. If you notice something else broken while you are in there, write it down and open an issue instead. Commit as you go with messages that say what changed, and push the branch when you are ready for eyes on it.

3. Open it, then expect comments

Describe what you changed and how you tested it. Comments on a pull request are about the code, not about you — the lead who reviews yours had the same comments on theirs last semester. Push follow-up commits to the same branch and the pull request updates itself.
Stuck for more than twenty minutes? That is the moment to ask in the project channel, not two days later. Nobody is keeping score.

A place to learn things the courses do not cover, with people at the same stage as you.

Interaction and style rules

Type: Space Grotesk for headings, Plus Jakarta Sans for interface and body, Newsreader for editorial moments, JetBrains Mono for metadata only. Navy #0A2033 for shell surfaces, green #2FA36B for action, #0B4A31 on #E4F6EC for beginner-friendly status, blue #1B4A72 for active, amber #B3651F for deadline urgency. Every status carries a glyph as well as a colour.

RULES
Rows over cards. Lists of comparable things are ruled rows; cards are reserved for a single featured item or a genuine grid of guides.
Dark is the frame. Header, page mastheads, and footer are navy. Content sits on white or #F7F8F6; the library uses warmer #FBFBF8.
Mono is metadata. Dates, counts, tags, kinds, and shortcuts only — never body copy, never headings.
Hover is a border, not a lift. Interactive rows brighten their background; cards shift their border to green. No shadows on hover, no transforms.
Touch targets ≥ 44px on mobile, and every filter, link, and card is reachable by keyboard in reading order.
